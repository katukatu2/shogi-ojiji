# 課題の達成状況の表示修正

作成: 2026-09-14 / Codex。起点: `d74cf72`。

戦法一覧で課題数を常に表示し、戦法ごとの分母を付けた。叱られた場合も課題数を消さず、同じ行にばかもんの回数を添える。360×640 の一覧の高さは、修正前後とも **303.4375px** で変化なし。保存済みの達成記録を削除する変更は行っていない。

## 修正前の再現

`tests/e2e/task-progress.spec.ts` に先に回帰試験を追加し、実装を変える前に Chromium で実行した。矢倉に 5 局・3 勝・ばかもん 2 回・達成課題 3 件・初勝利の免状を保存し、対局設定へ進んだ。

期待する成績行は `3勝 5局` と `課題 3/8・ばかもん 2回` だが、実際には `3勝 5局` と `ばかもん 2回` だけだったため、試験は失敗した。修正後は同じ試験が Chromium / WebKit とも成功した。

証拠は `logs/task-progress/before-fix.txt`、`before-fix-results.json`、`before-fix-artifacts/`。修正前の画面と寸法も `before-*-*.png`、`before-layout.json` に保存した。

## 変更内容

実装の変更箇所は `src/ui/settings.ts` の成績表示だけ。

| 状態 | 表示する成績行 | 行数（免状の行を除く） |
|---|---|---|
| 未対局 | 未対局・課題 0/8（棒銀は 0/7） | 1 |
| 対局あり・ばかもん 0 回 | 3勝 5局 ／ 課題 3/8 | 2 |
| 対局あり・ばかもんあり | 3勝 5局 ／ 課題 3/8・ばかもん 2回 | 2 |

分母は `tasksFor(style).length`。分子は、その課題一覧の中で `doneTaskSet(progress)` に達成記録があるものの数とした。単純に上限へ丸める方式では、未知の課題が実在する課題の達成と誤認されるため、表示時に現在の課題との照合を行う方式を選んだ。

これにより、棒銀の有効な課題 7 件に未知の ID と重複 ID が混ざっていても `7/7` になる。四間飛車の有効な課題 1 件と未知の ID 1 件は `1/8` になる。表示数の分母超過を防ぎながら、元の `tasksDone` は保持する。試験では強さの変更による再保存まで行い、未知・重複 ID を含む配列が削除されないことを確認した。別の版へ戻した際に、今回の修正が原因で達成記録を失う不可逆な保存移行はない。

## 画面の高さと説明の幅

同じ保存データ、同じブラウザ、同じ画面寸法で、実装修正の前後に計測した。保存データは再現に使った矢倉、四間飛車、未対局の残り 3 戦法である。免状も同じ条件にした。

| ブラウザ | 画面寸法 | 一覧の修正前 | 一覧の修正後 | 差 | ページ全体の高さ（前後同じ） |
|---|---|---:|---:|---:|---:|
| Chromium | 360×640 | 303.4375px | 303.4375px | 0px | 673px |
| WebKit | 360×640 | 303.4375px | 303.4375px | 0px | 673px |
| Chromium | 390×844 | 303.4375px | 303.4375px | 0px | 844px |
| WebKit | 390×844 | 303.4375px | 303.4375px | 0px | 844px |

各行の高さも前後で一致した。360×640 のページは今回の免状つき保存データでは 33px スクロールする。指示書の 24px とは測定条件が異なるため、今回の同条件の前後比較値を記載している。横方向のはみ出しはない。

360px 幅で、最も幅を使う矢倉の成績行を足した後の説明欄は Chromium で **178.484375px**、WebKit で **178.046875px**。修正前はそれぞれ 232.171875px、231.734375px だった。説明は冒頭の「金銀三枚の堅い囲い。」とその先まで読め、戦法名・成績・課題数・ばかもん・初勝利の札も表示できている。他の戦法の説明欄は 209.296875px 以上を保った。390px 幅では矢倉も約 208px ある。

CSS の変更は不要だった。`em` の nowrap、免状、行数を維持し、説明欄は従来の省略記号を使っている。画像は両寸法・両ブラウザで取得し、360×640 の Chromium と 390×844 の WebKit の画像を目視でも確認した。

実測スクリプトは `logs/task-progress/measure.mjs`。前後の JSON、画像、差分照合結果 `verified-summary.json` を同じディレクトリに保存した。

## 追加した試験

`tests/e2e/task-progress.spec.ts` に 7 件を追加した。既存の操作試験と同じ保存データの読み込み・画面描画を通し、これまで試験がなかった `.joseki-btn` の成績表示そのものを検査するため、この場所を選んだ。

1. ばかもんがある戦法の課題数・ばかもん回数の同時表示と、免状の維持。
2. ばかもんがない戦法の課題数と、ばかもん表示がないこと。
3. 未対局の課題数・分母が 1 行で表示されること。
4. 棒銀は 7、他 4 戦法は 8。期待値は `tasksFor` から生成せず、数値を直接記述。
5. 未知・重複 ID が表示数を増やさず、再保存しても元の記録を残すこと。
6. 360×640 で行数・nowrap・説明欄の幅・一覧と各行の高さを確認。
7. 390×844 でも同じレイアウト条件を確認。

高さの回帰試験は、現在の画面の実測後、同じ画面の成績文字列だけを起点の表示に戻して比較する。免状は残す。フォントの環境差による固定ピクセル値への依存を避けつつ、行追加による高さの増加を検出する。別途、上表の実装修正前後の計測も実施した。
