# Codex 向け作業指示書: 開発時の Service Worker キャッシュをやめる

作成: 2026-09-12 / 作成者: Claude（査読担当）
起点: `57745d5`

## 背景

ユーザーが `npm run dev`（Vite 既定の **5173**）で遊んだところ、次の症状が出た。

- 「対局開始」の帯の文字が出ない。
- 盤の駒が動かない。
- 駒音が鳴らない点だけは直っていた（＝新しいコードの一部は効いていた）。

私は 5178（`.claude/launch.json` の設定）で、次の 4 通りを試して**再現しなかった**。

1. 保存データなし・設定画面経由
2. 保存データあり・「前回の設定で始める」経由
3. 開発サーバーを停止した状態（Service Worker のキャッシュから配信）
4. 製品ビルド（`npm run build` を `serve-static.mjs` で配信）

いずれも帯が出て、実際のタップで ▲７六歩 が指せ、オジジが △８四歩 と応じた。帯は `pointer-events: none` なので操作を妨げず、盤の当たり判定に重なる要素も無かった。コンソールのエラーも無い。

**違いはポートそのものではなく、オリジンごとに残る Service Worker のキャッシュである。**

## 確認した事実

開発時にも Service Worker が登録され、**開発中のソースをキャッシュしている**。5178 のキャッシュを開くと 48 件入っていた。

```
/  /src/main.ts  /src/style.css  /@vite/client  /raizo/assets.js  …（計 48 件）
```

`public/coi-serviceworker.js` の該当箇所は次の 3 つ。

| 行 | 内容 |
|---|---|
| `:166` | `if (complete \|\| VERSION === 'development') hit = await cache.match(req, …)` — 開発時もキャッシュを引く |
| `:171-173` | `if (VERSION === 'development' && res.ok && cache) { await cache.put(req, res.clone()); }` — 開発時も保存する |
| `:176-178` | `const fallback = hit \|\| …; if (fallback) return cachedResponse(fallback, req);` — **取得が失敗したらキャッシュを返す** |

取り出す順はネットワーク優先なので、サーバーが動いている間は新しいファイルが出る。しかし**開発中は `npm run dev` の停止・再起動でネットワーク取得が失敗するため、そのときだけ古いファイルが混ざる**。新しい CSS と古い `main.ts` が組み合わさると、画面は描けるのに帯が出ず、盤のタップも効かない、という今回の症状になる。

キャッシュは**オリジン単位**で残る。ユーザーは一貫して 5173 で `npm run dev` を使ってきたので、5173 のキャッシュにはこのアプリの初期の版から積み上がったファイルが入っている。私が使っていた 5178 は比較的新しく、そのため再現しなかった。

**開発時にキャッシュを持つ理由は無い。** `vite.config.ts` は `server` と `preview` の両方に COOP/COEP ヘッダーを設定している（`isolationHeaders`）。開発と `vite preview` では Vite 自身がヘッダーを付けるので、Service Worker の役目は無い。実際、開発時のキャッシュは「取得に失敗したら古い版を返す」ためだけに使われている。**開発中は古い版を返すのではなく、エラーを出すべきである。**

**この欠陥が残った理由もはっきりしている。** `src/sw.test.ts:53` は読み込み時に必ず `VERSION` を実際の版へ差し替えるので、**開発分岐は一度も試験されていない**。

### 因果について正直に書く

上の「仕組み」はコードとキャッシュの実物で確認した。ただし**ユーザーの画面が壊れた瞬間を直接観測してはいない**。再現は 5173 のキャッシュ状態に依存するため、まず下の「再現」を先に実施し、確認できたことと確認できなかったことを分けて報告してほしい。

## 作業

### 1. 先に再現する

指示書の慣例どおり、直す前に欠陥を再現する試験を作る。

- 開発版（`VERSION = 'development'` のまま）の Service Worker を読み、キャッシュに古い `/src/main.ts` を入れた状態でネットワーク取得を失敗させると、**古い内容が返る**ことを確かめる。`src/sw.test.ts` の既存の枠組み（`worker()` と `setOffline`）が使える。`VERSION` を差し替えずに読み込む経路を足す必要がある。
- 実ブラウザでも確かめられるなら望ましい。`npm run dev` で開いてキャッシュを作り、サーバーを止めて再読み込みし、キャッシュの `/src/main.ts` を古い内容に差し替えてから読み直す、などの手順で観測できる。できなければ単体での再現で足りる。理由を報告すること。

### 2. 開発時はキャッシュを持たない

**推奨する形**: 開発時も Service Worker は登録するが、**素通し（ヘッダーを付けるだけ）**にする。

- `:166` の `|| VERSION === 'development'` を外す。開発時は `hit` を引かない。
- `:171-173` の開発時の `cache.put` を外す。
- `:176-178` の代替取得は、開発時には使わない（`complete` が真のときだけ代替を返す形にする）。取得の失敗はそのまま投げる。

**自己修復を入れること。** ユーザーの 5173 には既にキャッシュが溜まっている。手で「Clear site data」をさせずに直るよう、**開発時は `activate` で自分のスコープの開発用キャッシュ（`prefix + 'development'`）を削除する**。

あわせて、開発時は `skipWaiting()` と `clients.claim()` を呼んで**即座に新しい Worker へ入れ替える**こと。現状 `install` は開発時に早期 return するだけで `skipWaiting()` を呼ばないため、新しい Worker は全タブを閉じるまで待機し、掃除が効かない。製品側の「既存タブの版を途中で変えない」方針は**変えないこと**（開発時だけ即時に入れ替える）。

**別案**: 開発時は Service Worker を登録しない。これも可。ただしページ側の分岐（`:182` の `else if`）からは `VERSION` が見えないので、両分岐から読める定数を足す必要がある。素通しにするほうが、登録経路を開発時も通せるぶん製品に近い。**どちらを採るかは任せる。選んだ理由を報告すること。**

### 3. 製品側は変えない

製品ビルドのオフライン保存は、直近の査読で内容まで確認した部分である。**次のどれも変えてはいけない。**

- 初回保存の失敗でも登録を残す挙動。
- 更新失敗時に動作中の旧版を守る挙動（`install` の throw）。
- 資源ごとの SHA-256 による再利用、実行版と最新待機版だけを残す整理、旧名 `ojiji-v\d+` の掃除。
- 音声の Range 応答（206 / 416）。
- 製品では `skipWaiting()` を呼ばない方針。

`npm run e2e:pwa` の 24 件が**そのまま通ること**が製品側を壊していない証拠になる。件数を減らしたり条件を緩めたりしないこと。

### 4. 開発分岐に試験を足す

現在ゼロなので、最低限これを入れる。

- 開発時は `cache.put` を呼ばない（キャッシュが空のまま）。
- 開発時に取得が失敗したら、キャッシュに古い内容があっても**それを返さずエラーになる**。
- 開発時は COOP/COEP ヘッダーが付く（素通しでもヘッダーは付ける）。
- 開発時の `activate` で既存の開発用キャッシュが消える。
- 製品時の挙動が変わっていないこと（既存の試験がそのまま通る）。

`src/sw.test.ts` の `worker()` は `VERSION` を必ず差し替えるので、**差し替えずに読み込む選択肢**を足すこと。

### 5. 開発ポートを揃える

今回の環境差の元になった点も塞ぐ。

- `.claude/launch.json` は `--port 5178 --strictPort`、ユーザーの `npm run dev` は Vite 既定の 5173。**同じオリジンで開発できるよう揃える。**
- 推奨は `vite.config.ts` の `server` に `port: 5173, strictPort: true` を置くこと。これならどの起動方法でも同じポートになる。`.claude/launch.json` もそのポートに合わせる。
- Playwright は 5179 / 5180 / 5181 / 5182 を使うので衝突しない。`strictPort` なので、埋まっていれば黙って別ポートへ移らずに失敗する。
- `README.md` の起動手順に、開発は 5173 であることを書く。

## 変えてはいけないもの（全体）

- オジジの 5 段階の台詞、一手につき台詞は一つ。
- 音は駒音と雷だけ。雷の音量 10%。オジジに声は付けない。
- タイトルは全身、対局は顔のみ。
- 固定素材（`public/raizo/`、`public/sfx/`、`public/engine/`）とクレジット表記。
- 「（公開先 URL）」に仮の値を入れない。
- 試験を `continue-on-error` などで黙らせない。

## 完了条件

1. 修正前に失敗する再現（単体、可能なら実ブラウザ）が用意され、修正後に消えている。
2. 開発時にキャッシュが作られない。既にあるキャッシュは、全タブを閉じずに自動で消える。
3. 開発時に取得が失敗したら、古い版ではなくエラーになる。
4. `npm run e2e:pwa` 24 件、`npm test`、`npm run e2e`、`npm run e2e:fullgame` がすべて通る。
5. 開発ポートが起動方法によらず同じになり、README に書かれている。
6. **ユーザーが `npm run dev` で 5173 を開き、Clear site data をせずに帯が出て駒が動くこと。** これが最終確認である。

## 報告

`docs/dev-sw-cache-response.md` を新規に作り、次を書くこと。既存の `docs/claude-*.md` は変更しない。

- 再現できたか。できなければ何を試して何が起きたか。
- 採った方式（素通し / 非登録）とその理由。
- 開発時の自己修復が、タブを閉じずに効くことをどう確かめたか。
- 製品側を変えていないことの根拠（PWA 24 件の結果）。
- ポートを揃えた方法。
- 未確認のまま残ったもの。

**自己評価で点数を上げないこと。** 記録を提出し、独立した査読で判定する。

## 査読側が確認する点（先に知っておくとよい）

- 開発時にキャッシュが 0 件であること（`caches.keys()` と各キャッシュの件数）。
- サーバーを止めた状態で再読み込みしたときに、古い版が表示されず素直に失敗すること。
- 製品ビルドで 24 件が通り、オフライン保存・更新・Range が以前と同じであること。
- `src/sw.test.ts` が開発分岐を実際に通していること（`VERSION` を差し替えていない経路があること）。
- ユーザーの手元で、Clear site data なしに直っていること。
