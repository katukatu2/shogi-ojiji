# Codex 向け作業指示書: 品質保証を 8 にする（CI の実行）

作成: 2026-09-12 / 作成者: Claude（査読担当）
現在の独立評価: 指導 8・ゲーム 7・リリース 7・品質保証 7

## 目的

**品質保証の残件は 1 つだけである。GitHub Actions のワークフローを実際に一度走らせ、緑にすること。**

型チェック、単体 338 件、操作 44 件、PWA 24 件、製品通し 1 件、自動対局 5 戦法はすべてワークフローに登録されているが、**一度も実行されていない**。設定が正しいという証拠が無い状態で、ローカルの成功件数を積み上げても品質保証は 8 にならない。

副次的に、一括実行時に Windows 版 WebKit が予期せず閉じた事象の切り分けも、CI（Linux）の結果と比べれば片付く。

**この指示書の範囲外**: 実機、APK・IPA、公開先 URL・連絡先の決定、ストア提出物、人の遊びの評価。これらはリリース準備・ゲーム完成度の残件であり、別件として扱う。

## 前提の解消（作業 0）

### 0-1. Git の書き込み拒否を直す

現在 `index.lock` を作成できず、**変更がコミットできていない**。作業フォルダーにしか成果が無い状態は復旧の面で危うく、CI に上げることもできない。

- `.git` への書き込みが拒否される原因を特定して報告すること（明示的な拒否 ACL、ウイルス対策のリアルタイム保護、OneDrive などの同期対象、ファイルのロック）。
- **セキュリティ設定を無断で変更して回避しないこと。** 原因を突き止め、変更が必要ならユーザーに提案して承認を得る。
- 直せない場合は、原因と試したことを報告し、代替（別フォルダーへ `git clone` して作業するなど）をユーザーに提案する。

コミットできるようになったら、現在の未コミット分を意味のある単位でコミットする。コミットメッセージは日本語。

### 0-2. 保存先の決定をユーザーに確認する

CI を走らせるにはリモートが要る。**公開先 URL が未定であることと、リポジトリを置くことは別の判断**である。次の 2 案を提示して、ユーザーに選んでもらうこと。**勝手に決めない。**

- **案 A: 非公開の GitHub リポジトリを作る。** CI はすぐ走る。GPL の対応ソース提供義務はバイナリを配布した時点で生じるので、配布前の非公開リポジトリは義務と矛盾しない。公開先 URL の決定を先送りしたまま CI だけ進められる。
- **案 B: 公開リポジトリにする。** CI が走るうえ、「（公開先 URL）」の空欄 5 か所（`src/main.ts`、`src/release.test.ts`、`docs/store/listing.md`、`README.md`、`public/privacy.html`）がそのまま埋まり、リリース準備の残件も 1 つ減る。ただし公開の判断はユーザーのもの。

既存の GitHub アカウント `katukatu2` の認証が通らなかった件も、あわせてユーザーに確認する。

**ユーザーが決めるまでは、案 C で先に進めてよい**（下記）。

### 0-3. 案 C: リモート無しで先に設定を検証する（決定待ちの間）

`act`（GitHub Actions をローカルの Docker で走らせる道具）でワークフローを実行し、**YAML の文法・ステップの順序・Linux での依存関係**を先に潰しておく。

```bash
# act の導入は Docker が要る。導入可否を先に確認して報告すること
act -W .github/workflows/ci.yml --container-architecture linux/amd64
```

**注意**: `act` で通ることは GitHub で通ることの証拠にならない（ランナーの中身、キャッシュ、artifact の扱いが違う）。**`act` の成功を CI 成功として報告しないこと。** あくまで前倒しのデバッグ手段である。

## 本作業

### 1. CI を走らせ、緑にする

リモートが決まったら、`main` を push してワークフローを起動する。手動起動（`workflow_dispatch`）も設定済みなので、そちらでもよい。

**落ちたら直す。落ちた原因と直した内容をすべて記録すること。** 想定される躓きどころを挙げておく。

| 想定される失敗 | 見るところ |
|---|---|
| Playwright のブラウザが無い | `npx playwright install --with-deps chromium webkit` が全 3 設定（e2e・pwa・fullgame）の前に走っているか。WebKit は Linux で追加の依存が要る |
| 製品通し試験が時間切れ | 2 コアのランナーではやねうら王が遅い。`timeout-minutes: 25` と Playwright の `globalTimeout: 20分` に収まるか。収まらなければ、上限を上げるのではなく **`maxPlies` を下げるか、CI では判定時間を短くする**ことを検討し、その判断を記録する |
| 自動対局が長すぎる | `--all-styles --games 2 --plies 60` は 10 局。ランナーの速度次第でジョブ全体が長くなる。所要時間を計測して記録する |
| ポートの衝突 | 5179 / 5180 / 5181 / 5182 が同一ジョブ内で順に使われる。前のステップのサーバーが残っていないか |
| artifact が空 | `logs/` は `.gitignore` 対象だが、実行時には生成される。`logs/fullgame`、`logs/ci-*.jsonl`、`logs/pwa/report` が実際に上がっているか |
| `release:artifacts` の失敗 | `dist` が先に作られているか。アイコンの colorType、版番号の 4 者一致、資源ハッシュ |

**やってはいけないこと**:

- 落ちる試験を `continue-on-error` や `--pass-with-no-tests` で黙らせること。
- 時間切れを、原因を調べずに上限を伸ばすだけで済ませること。
- 「（公開先 URL）」に仮の値を入れて `release:check` を通すこと。この失敗は意図されたもので、公開情報が決まるまで失敗し続けてよい。

### 2. 緑になったら、安定していることを確かめる

**一度通っただけでは足りない。** 同じワークフローを**連続 3 回**走らせ、3 回とも緑であることを確認する。1 回でも落ちたら、それが flaky なのか環境依存なのかを切り分けて直す。

製品通し試験は毎回棋譜が変わる（これまで 43 手・63 手・73 手・79 手）。手数が違っても詰みまで完走することを 3 回とも確認する。

### 3. WebKit の異常終了を切り分ける

Windows での一括実行時に WebKit が予期せず閉じた事象について、次を確かめて結論を出す。

- CI（Linux）で操作試験 44 件を 3 回走らせ、WebKit が落ちるか。
- 落ちなければ **Windows 固有**と結論づけ、その旨を記録する。ローカルの日常確認から Windows WebKit を外すか残すかをユーザーに提案する。
- 落ちれば、失敗したときのトレースと動画を artifact から取得し、どの操作で閉じるかを特定する。

## 完了条件

次のすべてを満たしたときに、品質保証の残件が片付いたとみなす。

1. 変更がコミットされ、リモートに反映されている。
2. GitHub Actions のワークフローが**実際に実行**され、**連続 3 回緑**になっている。
3. 実行の URL、所要時間、各ステップの時間、artifact の一覧が記録されている。
4. 途中で落ちた項目があれば、原因と修正内容が記録されている。試験を黙らせた箇所が無い。
5. WebKit の異常終了について、Linux で再現するかの結論が出ている。

## 判定のときに確認する点（査読側の視点）

次の再査読では、報告された run を実際に見て次を確かめる。あらかじめ知っておくとよい。

- run が本当に存在し、`main` の該当コミットに対して走っていること。
- 全ステップが実行されている（`skipped` や `continue-on-error` で素通りしていない）こと。
- 製品通し試験が実際に詰みまで到達し、artifact に `result.json` と画像が残っていること。
- 自動対局の artifact が 5 戦法 × 2 局を含み、error 行が 0 であること。
- ローカルの成功記録を CI の成功として数えていないこと。
