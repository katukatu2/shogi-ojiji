## 1. 未保存案内が画面内にあるか — 修正確認

**実測（自分で計測。360×640、配信ヘッダーあり、manifest 障害）**

| 項目 | 値 |
|---|---|
| 案内の位置 | top 0 / bottom 56（画面内） |
| body の上余白 | 56px |
| 初期スクロール | x 0 / y 0 |
| 盤の位置 | top 213 / bottom 533（案内と重ならない） |
| 結果画面の板 | top 141 / bottom 555（画面内、案内と重ならない） |

前回は top 876・画面高 844 で画面外だった。`document.body.prepend` と `position: fixed` で上部に固定され、`ResizeObserver` が実寸を `--offline-status-height` に流し、`body` の余白・盤幅・`.overlay` の inset・各画面の `min-height` がその値を引くようになっている。保存が成功すると余白は 0 に戻る。

**試験の強度**: `tests/pwa/recovery.spec.ts` が 3 障害 × 配信ヘッダーあり/なし × 390×844 と 360×640 の 12 通りで、案内・盤・4 つの操作ボタンすべてに `toBeInViewport({ ratio: 1 })` を掛け、案内の下端 ≤ 盤の上端、スクロール 0 も検査している。表示中の幅変更と文字拡大（20px）、保存復旧後の余白 0 も含む。前回この欠陥を素通りさせた `toBeVisible()` は、位置が画面外でも通る。今回の `toBeInViewport({ ratio: 1 })` は、旧実装の値（top 876 / 画面高 844）ならば ratio 0 で必ず失敗する。**同じ後退はもう素通りしない。**

副産物として、前回の CSS 追加で `html,` と `#offline-status` が同じ組になり `html` に案内用の余白と最大幅がかかっていた誤りも直っている。これは私が前回見落としていた。

**自動試験が見ていない範囲を実測**: 案内が出ている状態で対局し投了して、結果画面の板が画面内に収まり案内と重ならないことを確認した（上表）。`.overlay { inset: var(--offline-status-height) 0 0 }` が効いている。

## 2. #9 の表示方針が実装と一致するか — 修正確認

**方針との一致**

- `SHALLOW_DEPTH`、`depthNote()`、`formatCp()` を削除。深さで留保の有無を分ける処理は残っていない。
- カットインは `形勢の目安 / 候補 ▲○○ → 互角 / 指した ▲△△ → 後手優勢` の形。振り返りは `reviewEvaluation()` が `形勢の目安（先手視点）: … → …`。どちらも `describeSide` の言葉だけ。
- 「正解」→「候補の手」に変更（カットイン `src/main.ts:888`、振り返り `src/ui/review.ts:46`）。
- 画面に残る数字は無い。`winProb` は `src/game/review.ts` の手の選定だけに使われ、`src/ui/` からは呼ばれていない（grep で確認）。

**内部を弱めていないこと**

- 判定閾値は全て不変（`LEVEL2_DROP` 150、`EVAL_DROP` 300、`LEVEL4_DROP` 700、`LEVEL5_DROP` 1200、`STILL_GOOD` 500、`TURNED_BAD` −150、`LEVEL2_MIN_AFTER` 150）。`severity()` に変更なし。
- `analysis` は `before / after / gap / depth / playedBest` を従来どおり保持。`depth` はコメントが「信頼度としては表示しない」に変わっただけで記録は残る。
- PV（`after.pv[0]` からの脅威の読み）と `EVAL_CLAMP` も不変。丸めた値を判定に流用していない。
- 試験は弱まっていない。深さの試験が `it.each([3, 12, 13, 14, 17, 20])` になり、**どの深さでも同じ表示になること**を証明する形に変わった。以前より強い。

**エンジンなしのときに形勢を作っていないこと**

`tests/pwa/fallback.spec.ts` が製品版でエンジンのスクリプトを落とし、「判定: 簡易」で実際に指し、形だけのカットインが出て `.evalline` が 0 件、結果画面の形勢カードが 0 件であることを検査している。`reviewEvaluation` は評価が無ければ「判定なし」を返す。**架空の形勢は作っていない。**

**前回指摘した逆転の解消**: 17 手読み 50→75 と 13 手読み 253→252 は、どちらも同じ言葉（互角 / 先手よし）になり、深さによる確実さの区別が消えた。表示の回帰試験に入っている。

**提案 2 を採らなかった判断**: 妥当。同じ候補が返ることは正しさの保証にならず、応答時間も変わる。実装していないものを「安定性を検証済み」と説明していない点も正しい。

**確認した副次的な性質**: 段階 4・5（カットインが出る条件）では、`describeSide` の言葉が候補側と指した手側で必ず異なる。落ち幅 300 以上かつ指した後が −150 未満、または落ち幅 700 以上で指した後が 500 未満、というどちらの経路でも、二つの値が同じ区分に入らないため。**カットインで「互角 → 互角」のような無情報な行は出ない。**

## 3. 履歴移動中の次画面表示 — 修正確認

`ScreenHistory.go()` が真偽値を返し、移動中は `false` を返して要求を `onAligned` に 1 件だけ保持する。`showSettings` と `startGame` は先頭で `if (!goToScreen(...)) return;` して描画を止める。移動が終わると保持していた最後の要求だけを呼び直す。

**試験の強度**: `tests/e2e/navigation.spec.ts:4-31` が `history.go` を 250ms 遅らせ、「タイトルへ」の直後に設定（さらに対局）を開き、`renderedEarly` が `false` であること、つまり**移動完了より先に次画面が描かれていない**ことを検査する。修正前は `showSettings` が即座に描画していたのでこの検査は失敗する。その後 1 回の「戻る」でタイトルへ戻ることも確認している。設定→対局と選び直す経路も含み、最後の要求だけが反映されることを見ている。

自分で走らせた操作試験は Chromium と WebKit の 44 件がすべて通過した。WebKit の異常終了は今回も起きていないが、Codex が申告するとおり**原因が解明されたわけではない**。

**自分で追った競合**: 移動中に「タイトルへ」を再度押すと保持中の要求が消えるが、その場合は画面も `screen` も title で一致するため不整合にならない。設定→対局と押し直した場合は最後の要求が残り、`align()` は二重に段を積まない。

## 所見（欠陥ではない）

振り返りカードの形勢行は、両側が同じ言葉になることがある。`winProb` の差が採用基準（8 ポイント）を超える組み合わせを 10 点刻みで全数調べたところ、31,082 通りのうち 1,982 通り（6%）で両側が同じ言葉になった。例は `−640 → −1400`（勝率 9→1）で「後手優勢 → 後手優勢」。

ただしこれは誤りではない。形勢の区分は実際に変わっておらず、変化の中身はすぐ下の説明文（`momentCaption`）が「ここで差が広がった」「互角の中で少し損をした」のように述べる。提案 1 を採ったことの当然の帰結であり、修正を求めるものではない。気になる場合の選択肢だけ挙げておく。形勢行に変化の大きさを言葉で足す、または敗勢の帯だけ区分を細かくする。**今回は対応不要と判断する。**
