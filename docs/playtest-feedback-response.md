## 3. 開始時の駒音と解錠の競合

- **再現**: `HTMLMediaElement.prototype.play` を記録し、修正前の開始操作で雷1回・駒音2回、いずれも呼び出し時は `muted=true` だった。これは再生APIの呼び出し回数であって、3回とも実際に聞こえたという報告ではない。開始の駒音と、同じ要素を停止・頭出し・ミュート解除する非同期の後始末が競合する構造も確認した。
- **変更**: `showStartBanner()` の `playPiece()` を削除した。`warmUp()` は10msの無音PCMを本番の2つの要素に再生し、駒音・雷の素材を開始時には再生しない。解錠中に要求された本当の音は、解錠用の停止と頭出しが完了するまで待たせる。
- **選択理由**: [WebKitの公式説明](https://webkit.org/blog/7734/auto-play-policy-changes-for-macos/)では、再生の許可は要素ごとに扱われる。専用の別要素を解錠しても本番要素に許可が移るとは限らないため、**本番要素を無音で解錠し、完了まで実再生を待たせる方式**を採用した。準備中に `muted` や音量を変更しないため、途中から音が出る後始末をなくせる。追加したPCMは全サンプル0の無音であり、新しい効果音ではない。
- **取消処理**: ミュート、タイトルへ戻る、雷による停止は、まだ解錠待ちの駒音も取り消す。同じ駒音への重複要求は新しい要求を残す。解錠が拒否された場合は後始末を行い、次の開始操作で解錠を再試行できる。
- **確認**: 両寸法で開始から最初の着手まで `koma.mp3` は0回、最初の着手で1回・`muted=false`。Chromium・WebKitの操作試験を追加した。遅延する解錠、停止・ミュート中の取消、雷との競合、解錠失敗を単体5件で確認した。駒音0.6・雷0.1を検査し、素材とクレジットは変更していない。
- **未確認**: 実物のiPhone/Androidでの再生許可や実際の聞こえ方は未確認。PC上のChromium・WebKitの再生呼び出しと状態を検証した。

## 4. 入玉の宣言・案内

### 再現

変更前に双方入玉・先手23点の局面で `enteringKing()` が `sente-loses` を返すことを再現した。後段の確認では、作業前の `0679c1f` の `main.ts`・`position.ts`・`title.ts` を検証専用のサーバーで読み、同じ局面から玉を1手動かすと、宣言操作なしで「持将棋」「後手（オジジ）の勝ち」になることも再現した。作業中のファイルを巻き戻してはいない。

片方の玉だけを敵陣に入れる場合は、旧画面に入玉の台詞・条件表示・宣言ボタンが出ず、対局が続いた。修正前の表示と結果は `before/old-rule-ui.json` と `old-rule-short.png` / `old-rule-entry.png` に保存した。

### 方式と理由

**27点法の入玉宣言**を採用した。片方だけの入玉から本人の選択で決着でき、相手との合意や指し直しを必要としない方式が、一人でオジジと遊ぶ本アプリに適していると判断した。

- [日本将棋連盟の対局規則 第9条](https://www.shogi.or.jp/match/taikyoku_rules/)では、合意による24点法と、31点以上で勝ち・24〜30点で指し直しとなる宣言法を区別している。旧実装の「双方入玉なら点数不足の側を自動負け」は、この宣言手順とは異なる。
- 採用した具体的な条件は [CSA・第23回世界コンピュータ将棋選手権の大会規定 第23条](https://www.computer-shogi.org/wcsc23/rule.html) に基づく。これをすべての棋戦に共通する唯一の規則とは扱わない。
- 自分の手番、自玉が敵陣3段以内、王手なし、敵陣に玉以外の自駒10枚以上、先手28点／後手27点以上。点数の対象は敵陣の自駒と持ち駒だけで、飛・角とその成駒が5点、玉以外の他の駒が1点。
- 本アプリは持ち時間制ではないため、残り時間の条件は設けない。千日手、連続王手の千日手、400手上限は従来どおり。24点法の合意による持将棋は今回採用しない。READMEにも同じ条件を記載した。

### 変更と検証

- `enteringKing(color)` は条件と点数を読むだけの処理になり、`declareEnteringKing(color)` が明示的な宣言の結果を判定する。共用していた `RuleEnding` の千日手判定は維持した。
- 自動終局の `ruleEnding()` から入玉判定を外した。プレイヤーの宣言ボタンは入玉後に表示し、自分の手番で条件がすべてそろうまで押せない。初心者が点数不足に気づかず宣言負けする事故を防ぐUIとした。ルール層では不成立の宣言を宣言側の負けとして単体検査している。
- オジジは自分の手番の開始時に自分の条件が成立している場合だけ宣言する。プレイヤーの点数不足を理由に終局しない。結果の帯にはどちらが入玉宣言したかを表示し、詰みと区別する。
- どちらかの玉が入玉すると、対局の操作ボタンの下に条件を表示する。入玉の一言は5段階の評価とは別に扱い、一手に一つの制限を守る。既に台詞・カットインが出た場合や吹き出しの間隔中は重ねず、次に話せる手に案内する。条件の表示自体はすぐ更新する。一度案内した側については、待ったで戻っても繰り返さない。
- 360幅で長い入玉の吹き出しが画面上端からはみ出すことを画像確認で見つけたため、入玉の説明だけは顔の横から下へ伸びる配置にした。
- 「遊び方」に入玉で詰まされにくくなることと宣言条件を追加。390×844・360×640で実際の文字列を確認した。
- 単体では27点法の条件成立・不足・王手・手番・敵陣の枚数・成駒の点数・盤の敵陣外を除外すること・片側入玉を検証した。旧24点法を前提とした期待値を変更した理由は試験内にも記した。
- 操作試験5件×2ブラウザーを追加した。入玉→条件表示→応手待ち→宣言→勝利と成績1局1勝、先手23点でも自動負けにしない、オジジの正当な宣言、王手中の無効化、待った後に説明を繰り返さないことを確認した。

### 実判定と限界

操作試験は入玉直前の局面の準備だけに `window.__ojiji` を使用する。初期配置から10枚を敵陣まで運ぶ長い棋譜にテストを依存させず、盤の操作と宣言・結果の接続を安定して調べるためである。準備後は盤とボタンを操作し、結果を直接設定していない。簡易Judgeも実際に通し、安全な入玉が段階1（悪手の文言なし）になることを確認した。

別途、実際のやねうら王・2スレッド・400msのJudgeで、入玉直前の局面から自動対局した。初期配置以外を読むため、試験用アダプターで基準SFENから棋譜を再生して実エンジンに渡し、評価値や指し手は模擬していない。記録した手順は `1d1c P*1b 2a1b+ 3i2i`。入玉後に歩打ちの王手を受け、受けてから29点・王手なしとなり先手が宣言勝ちした。入玉の手と王手を受ける手のJudgeには誤った悪手の文言は出なかった。証拠は `entering-engine-selfplay.json`。この1局面の観測を、すべての入玉局面の解説の保証にはしない。

初期配置から入玉までを人の操作だけで進めた製品試験は未実施。通常の初期配置から詰みまでの製品通しは別途成功した。オジジが入玉を目指す手選びへの変更はしていない。

### 検証中の失敗と対処

1. 追加した「入玉の一言を繰り返さない」試験が最初は両ブラウザーで失敗した。原因は `.bubble:visible` が存在しない正しい無言の状態に対し、否定の文字列照合で要素の存在を要求したこと。可視の入玉メッセージの件数が0であることを直接確認する形に直し、全56件を再試行なしで実行し直した。初回のログ・JSON・トレース・動画は `e2e-first-full-attempt/` に残した。
2. PWAの24件終了後、テスト用サーバーの停止待ちが残った。診断ログには `Terminating the WebServer` があり、次の終了通知が出ていなかった。Windows版Playwrightはこの箇所で子プロセスをtaskkillで回収する。自動回収が完了しなかったため、起動ログに記録された当該実行のサーバーPIDだけを確認して終了させると、正式なJSONレポートの出力と終了コード0まで進んだ。最終実行では15:47:54.999に終了待ち、15:48:40.871に回収完了。試験本体やブラウザーを成功扱いで打ち切ったものではない。Windowsの無介助でのサーバー回収は未解決であり、CI側の設定は弱めていない。
3. 通常の単体・ビルドは、このサンドボックスで既知の設定読み込みエラーが続く。設定ファイルの読み込み方法だけをローカルコマンドで変えて検証した。CIの標準コマンドは変更していない。
