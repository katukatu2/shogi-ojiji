## 1. 対局設定の「オジジの強さ」の説明文を消す

**ユーザーの言葉**: 「オジジの強さの説明文は必要ない。」

**現状**: `src/ui/settings.ts:53` が `levelById(progress.level).description` を `.level-desc` として出している。見習いなら「オジジは手を抜く。駒組みは本気だが、そのあとは大らか。まず一勝を。」のような 2 文。

**やること**: `.level-desc` の行を消す。

**残すもの**: 直後の `.level-next`（`promotionLine(progress)`、例「昇級まで: あと 2 勝・課題 3」）は**残す**。これは以前の査読で「昇級条件が画面のどこにも出ていない」と指摘して足したもので、説明文とは別の情報である。

**注意**: `LEVELS` の `description` 自体は消さないこと。`src/game/progress.test.ts` が参照している可能性があるので、消すのは画面への出力だけ。テストが落ちたら、テストではなく変更の方を見直す。

**完了条件**: 対局設定画面に強さの説明 2 文が出ない。昇級までの行は出る。`npm test` と `npm run e2e` が通る。

## 2. 対局設定の戦法プレビュー（盤面画像と説明）を消す

**ユーザーの言葉**: 「戦形のスクショと説明は必要ない。画面がごちゃごちゃしてしまう。」

**現状**: `src/ui/settings.ts:94-115` の `.preview` が、選んだ戦法について次の 6 つを縦に並べている。

1. `miniBoard(formationOf(style))` — 駒組みの小さな盤（＝ユーザーの言う「スクショ」）
2. `${style.name}の駒組み` と「まずは○○型。対局ごとに形を変えてくる。」（＝「説明」）
3. 成績（勝数・局数・ばかもん回数）
4. 次の課題
5. 次の免状の条件
6. 皆伝の条件

戦法の一覧（`.joseki-btn`）にも名前・短い説明・成績・免状が出ているので、3 と 5 は重複している。

**やること**:

- **1 と 2 を消す。** 盤の画像と駒組みの説明文。ユーザーが名指しした部分。
- **3 と 5 を消す。** 一覧の行にすでに出ている。
- **4（次の課題）と 6（皆伝の条件）は残す。** どちらも他に出る場所が無い。`.preview` を 1〜2 行の小さな帯に作り替えて、この 2 つだけを出す。盤の画像を消すので `.preview` の横並びレイアウト（`display: flex` と `gap: 18px`）も要らなくなる。`src/style.css` の該当部分を整理すること。
- `miniBoard` と `formationOf` が設定画面から使われなくなる。他に使っている場所が無ければ、未使用の import と関数を残さないこと（`src/game/formation.ts` とその試験の扱いは、他から参照されていないか確認してから決める）。
- 戦法を選んだときの `preview.scrollIntoView`（`:87`）は、帯が小さくなるなら不要かどうか実機の見え方で判断する。

**判断が要る点**: 4 と 6 を残す配置は任せる。ただし**この 2 つを画面から消してはいけない。** 以前の査読で「昇級条件と皆伝の条件が見えない」を欠陥として指摘し、その対応として入れたものなので、消すと後戻りになる。置き場を変えるなら、変えた場所を報告すること。

**完了条件**: 設定画面に駒組みの盤と駒組みの説明が出ない。次の課題と皆伝の条件は引き続き読める。390×844 と 360×640 で戦法一覧・強さ・開始ボタンが縦スクロールなしか、少ないスクロールで収まることを実機の寸法で確認する。

## 3. 対局開始時に駒音が鳴るのをやめる

**ユーザーの言葉**: 「対局開始時に駒音が鳴っている。」

**現状（こちらで再現済み）**: `src/main.ts:272`、`showStartBanner()` の中で `playPiece()` を意図的に呼んでいる。「対局開始」の帯の効果音として入れたもの。

ブラウザで `HTMLMediaElement.prototype.play` を差し替えて記録したところ、対局開始時に 3 回鳴っていた。

```
bakamon_thunder.mp3  muted=true   at 16579.66   ← warmUp
koma.mp3             muted=true   at 16579.85   ← warmUp
koma.mp3             muted=true   at 16593.15   ← showStartBanner の playPiece
```

**付随する不具合**: 3 回目は `muted=true` の状態で再生が始まるが、その直後に `warmUp()` の `.finally(() => { x.muted = false; })`（`src/ui/audio.ts:99-101`）が走って**再生の途中で音が出る**。頭が欠けた駒音になる。`playPiece` を消せばこの症状も消えるが、**`warmUp` の解錠と実際の再生が競合しうる構造自体は残る**ので、あわせて直すこと。

**やること**:

- `showStartBanner()` の `playPiece()` を消す。対局開始の帯は無音にする。
- `warmUp()` を、解錠中に別の再生が始まっても音量や muted を壊さない形にする。案としては、解錠専用の `<audio>` を 1 つ用意して本番の 2 つと分ける、または解錠が終わるまで `playPiece` / `playThunder` を待たせる。**どちらを採るかは実装者の判断でよいが、選んだ理由を報告すること。**

**変えてはいけないもの**: 駒音そのもの（駒を動かすたびに鳴る）、雷の音量 10%、素材ファイル、クレジット表記。

**完了条件**: 対局開始から最初の着手までの間に `koma.mp3` の再生が 1 度も起きない（`play` を差し替えて数える形で確認する）。最初の着手では従来どおり鳴る。tests/e2e か tests/pwa に、開始時に駒音が鳴らないことの回帰試験を 1 本足すこと。

## 4. 入玉のルールを、遊ぶ側から見て機能する形にする

**ユーザーの言葉**: 「入玉のルールが組み込まれて無い。」

**現状**: 実装は `src/engine/position.ts:439` の `enteringKing()` にあり、`src/main.ts:657` の `ruleEnding()` から毎手呼ばれている。しかし遊ぶ側から見ると機能していない。理由は 3 つある。

### 4-1. 宣言していないのに負けになる（ルールの誤り。最優先）

`enteringKing()` は条件がそろうと 24 点法で判定し、点数が足りない側を負けにする（`points[0] < 24 → 'sente-loses'`）。`ruleEnding()` はそれを `endGame('lose', '持将棋')` に変える。

**宣言法では、宣言していない側が点数不足で自動的に負けになることはない。** 宣言は指す側の選択であり、条件を満たさずに宣言したときに負けになる。現状はプレイヤーが何もしていないのに負けを宣告されうる。

**やること**: 自動で勝敗を付けるのをやめる。条件がそろったときに**プレイヤーが「持将棋を宣言する」を選べる**ようにし、押したときだけ点数で判定する。オジジ側は、条件を満たしていて自分が勝ちか引き分けになるなら宣言してよい。

### 4-2. 片方だけ入玉しても何も起きない

`enteringKing()` は両方の玉が敵陣にいることを最初の条件にしている（`:442`）。初心者がオジジと指して、双方が玉以外の駒を敵陣に 10 枚以上入れる終盤に至ることはまずない。**プレイヤーの玉が敵陣に入っても、画面には何の反応も無く、400 手の上限まで対局が続く。**

**やること**: 自玉または相手の玉が敵陣に入ったら、オジジが一言で状況を伝える。何が起きたのか、勝ちにするには何が要るのかが分かる文にする。台詞は一手に一つの決まりを守り、既存の 5 段階の台詞とは別物として扱う。既に入玉していることを繰り返し言わないこと。

### 4-3. プレイヤー向けの説明が無い

`入玉` `持将棋` `宣言` という語は、画面に出る文字列としては結果画面の「両方の玉が入玉した」（`src/main.ts:980`）しか無い。タイトルの「遊び方」（`src/ui/title.ts:66-72`）にも項目が無い。

**やること**: 「遊び方」に 1 行足す。長い説明は要らない。玉が敵陣に入ると詰まされにくくなること、条件を満たせば宣言で決着できることが分かればよい。

### 実装上の注意

- **点数法をどれにするか（24 点法か 27 点法か）は調べてから決め、根拠を報告すること。** 現在は 24 点法だが、宣言法として一般に使われるのは 27 点法である。どちらを採るにせよ、`README.md` の記述と実装を一致させること。
- `enteringKing()` の戻り値の型 `RuleEnding` を変えるなら、`src/engine/position.test.ts` の既存の試験（王手中は成立しない、敵陣の駒が足りなければ成立しない、点数計算）を壊さないこと。壊れる場合は、なぜ前提が変わったのかをテストのコメントに書く。
- 千日手・連続王手の千日手・400 手の扱いは変えないこと。
- **オジジ側の指し手**は今回の範囲外でよい。オジジが入玉を目指すようになる必要はない。ただし、プレイヤーが入玉したときにオジジの判定（`src/style/judge.ts`）がおかしな説明を出さないかは、自動対局か製品通しで一度確かめること。

**完了条件**:

1. プレイヤーが宣言していないのに持将棋で負けにならない。
2. 玉が敵陣に入ったときに、画面で何か分かる反応がある。
3. 条件を満たしたときに宣言でき、宣言すると結果画面まで進む。
4. 「遊び方」に入玉の行がある。
5. 単体試験に、宣言の条件を満たす局面・満たさない局面・王手中の局面の 3 つを足す。
6. 入玉から宣言までを通す操作試験を 1 本足す（`window.__ojiji` に頼らず盤を操作するのが望ましいが、局面の作り方が難しければ単体試験で代替してよい。その場合は理由を報告する）。
